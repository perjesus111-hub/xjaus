# Controlled non-publishing consumer: design, not approval

## Decision

Do not enable or implement a production consumption path yet. The current in-process SquashFS parser is not resource isolated, the separate worker prototype does not pin its executable and is not integrated, and no independently approved AppRun reference or production trust anchor exists. `verify_release` and `production_verify` must continue to reject unconditionally. The existing test-only fixed-consumer prototype internally uses a callback and reopens staged paths during validation; it is not the design below. No production key, publication path, CLI, or `runLocal` change is authorized by this document.

## Threat model and boundary

The design is conditional on a trusted host, kernel, process, implementation and dependencies; an authenticated policy and key provisioned independently; and a staging tree kept quiescent for the entire acquisition and validation interval. A malicious same-UID process, writable mappings to the staging tree, transient substitutions, and concurrent in-place writes violate that assumption. Descriptor identity and enumeration checks do not establish quiescence or an atomic filesystem snapshot. This design does not sandbox hostile Rust code: a function, type, or private field cannot stop code in the process from opening paths, calling syscalls, or leaking data. Stronger adversary models require a separately designed OS-enforced isolation boundary and a different review.

## Proposed single controlled flow

1. Use a source-embedded, independently approved policy binding the exact release version, full commit, exact ordered path set, trust anchor, resource limits and independently reproduced AppRun reference. Missing or ambiguous policy means reject; no runtime caller-provided policy, trust key, parser executable, callback or reference may override it. No such approved policy currently exists.
2. Authenticate the complete bounded canonical manifest with the approved key before trusting its records. Reject malformed signatures, unsupported domains or versions, noncanonical encodings, wrong commit, reordered/duplicated/extra paths, zero or excessive sizes, overflow and trailing bytes. Each signed record binds the exact ordered path, length and SHA-256 digest. Limit aggregate bytes before allocation or reads.
3. In trusted quiescent staging, open the root and fixed components descriptor-relatively with no symlink following; require exactly the expected directory entries and regular files. Copy each candidate into a new memfd with an explicit length bound. Apply and check write, grow, shrink and seal seals; independently measure length and hash the sealed bytes against its authenticated record. Handle all errors by rejecting and closing all acquired descriptors. Host memory/storage availability, inode/link policy and supported kernel behavior need explicit review.
4. Complete any staged-tree identity and entry checks before the boundary; these checks cannot cure a violated quiescence assumption. After that boundary, discard all staging descriptors and pathnames. No reopen, directory traversal, candidate path lookup or caller-controlled callback may occur after validation. Only sealed descriptors and authenticated metadata cross into the fixed consumer; implementation and all transitive callees must be reviewed for this invariant. Do not rely on Rust types to enforce it against hostile code.
5. Compare AppRun extracted from the sealed AppImage against the approved independent reference using an independently reviewed, resource-isolated parser. The parser must consume that same sealed snapshot, not reopen a staging path; its executable identity and result protocol must be authenticated, and its failure, timeout, crash, malformed output or resource-limit setup failure must reject. CPU, memory, wall time, descriptors, descendants and input acquisition limits require an explicit design and adversarial validation. The existing worker prototype is not this component and is not a sandbox.
6. Only after every check succeeds, invoke one fixed, in-tree, non-publishing consumer directly, without callback, plugin, generic trait dispatch to caller code, or user-supplied executable. It reads the sealed descriptors and authenticated metadata only; no candidate path access or external side effects. A suitable first operation is a bounded integrity report, explicitly not a release approval. A report must not be returned on partial failure. This is an implementation/review contract for trusted code, not confinement.

No publication, signing, uploading, execution of candidate bytes, shelling out to candidate-provided tools, CLI exposure or `runLocal` integration is implied. Any future enablement requires a separate explicit authorization and independent security review, not merely passing tests.

## Adversarial acceptance tests required before implementation can be enabled

- Verify production entry points reject with missing policy, including otherwise valid test-signed inputs; test keys must never become trusted production material.
- Test signed malformed manifests: truncation at every field, invalid signature/key, wrong domain/version/commit, duplicates, order changes, paths including traversal, suffixes, extra records and trailing bytes, integer overflow, zero and oversized lengths, and aggregate limit violations.
- Exercise symlinks at each component, non-regular files, extra/missing entries, directory and file substitution during pre-boundary checks, short/long/mutated input, failure to allocate or seal, and each missing seal. Quiescence violations are not claimed to be fully detectable.
- Replace or unlink source paths immediately after the boundary in a controlled test and demonstrate the fixed consumer reads only the original sealed bytes. Instrument open/openat/openat2 and equivalent path-access syscalls across the complete post-boundary flow; assert no staged-path reopening. This verifies observed implementation behavior, not sandboxing.
- Tamper each sealed-descriptor/record pairing, length and digest; ensure rejection without a report. Test FD ordering and shared file-offset interactions, using offset-independent reads or exclusive ownership. Verify sealing blocks writes, resizing and later seal changes.
- Exercise isolated-parser executable substitution, bad protocol, missing/duplicate/nonregular AppRun, corrupt images, reference mismatch, worker crash/hang, resource exhaustion, deadline and descendant cleanup. Establish kernel and process isolation assumptions independently; tests alone cannot prove them.
- Check no success/report or side effect on any failure and that no production entry, CLI, publisher or `runLocal` was enabled. Run full offline and locked suites and document skipped tests and environmental limitations.

## Explicit gaps

No production controlled consumer or authenticated policy exists; test-only `verify_fixed` is not the proposed no-callback architecture. No approved AppRun provenance/reference or production key is present. The parser lacks the required integrated isolation and worker identity binding. No post-boundary syscall audit, adversarial integration suite, full resource accounting or independent security review has been completed. Therefore this document is a design and rejection rationale, not an implementation, security proof, or release approval.
