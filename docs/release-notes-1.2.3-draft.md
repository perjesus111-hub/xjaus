# XJAUS 1.2.3 — draft, not published

## Changes

- Linux windowed mode uses the desktop compositor's native title bar, including on the login screen. Its appearance follows the desktop theme. Wayland controls final placement.
- The Linux AppImage filename is `XJAUS-1.2.3-x86_64.AppImage` and it uses the static type-2 runtime (appimage toolset `1.0.3`, runtime 20251108); the runtime is a static-pie ELF with no dynamic `NEEDED` entries. Black-and-gold styling remains the default on dark systems, and the interface now follows a light system theme.
- The supported Linux packaging path hardens the generated AppRun to refuse a failed or missing user-namespace probe and the `--no-sandbox` argument. It checks the complete launcher using an external 7z SquashFS reader. Direct electron-builder invocations bypass this wrapper. The check can reject hosts where another sandbox mechanism could work; it does not prove all sandbox layers are active on all distributions.

## Packaging and validation limits

- AppImage, RPM and DEB were built locally; the NSIS EXE was rebuilt after the Windows sidecar crate was bumped to 1.2.3. The MSI built after copying the 32-bit mingw runtime DLLs (`libgcc_s_dw2-1.dll`, `libwinpthread-1.dll`) from the mingw32 sysroot into the disposable Wine prefix's `syswow64`, which let WiX's `candle.exe` load wine-mono. Both installers are unsigned; they were built with Wine tooling, but installer execution under Wine or native Windows has not been verified. These artifacts are not yet approved for release.
- A prior NSIS payload was extracted and inspected, but it is not established that its hash matched the subsequently rebuilt installer. Re-extract and audit the exact final installer, including ASCII and UTF-16 private-path scans, before release.
- The AppImage catalog bot tested v1.2.2 and passed it with warnings: an old runtime requiring host libc and libfuse2, a glibc 2.39 reference, redundant `linux` in the filename, a dark window on a light-theme test system, and no AppImageUpdate information. The original report is the AppImage catalog PR 10806 bot comment 6504521652; full job log is GitHub Actions run 40926999978. In 1.2.3 the filename, the static runtime and the system-theme behavior are addressed; the glibc reference belongs to Electron's own baseline and is unchanged, and AppImageUpdate information remains excluded.
- The bundled runtime no longer links host libfuse2: `readelf -d` on the built artifact shows a static-pie ELF with zero `NEEDED` entries (type2-runtime commit dd6cebe), and the same build's `--appimage-version` works. A negative test on a host without libfuse2 was not performed (the build host has `fuse-libs` installed). `--appimage-extract-and-run` remains an alternative where supported. The glibc 2.39 reference and the actual minimum distro compatibility remain unverified; the runtime upgrade alone does not change Electron's or the sidecar's baseline.
- AppImageUpdate update information and `.zsync` are not included in the release build. An experimental separate preparation script exists, but it does not authenticate the publisher: adjacent SHA-256 and zsync SHA-1 values can be replaced alongside the artifact. A trusted signing/verification policy and a live GitHub release update test remain required; do not treat local test results or electron-builder's blockmap as authenticated differential updates. Additionally, the script's pinned appimagetool snapshot (SHA-256 `793fca0c…`) is no longer downloadable: the continuous asset was rebuilt (current hash `e8c1169c…`) and the 1.9.1/1.9.0 tagged assets also hash differently, so a real-artifact embedding test needs a newly verified pin; the pin was deliberately not rotated by an agent.
- An isolated native-Wayland login instance was checked at scale 300%: the user reported that mouse dragging worked, but the compositor position change was not independently captured. Two synthetic F11 cycles returned the compositor window to its prior dimensions in that instance; maximization was not independently verified. Login controls, exact position restore, dashboard drag, physical controller, authenticated playback, physical 21:9 and native Windows remain unverified.
- The original full AppImage report must be checked before claiming its entire warning list has been resolved.
